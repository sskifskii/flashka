# Процесс разработки Flashka

Этот документ задаёт прагматичный процесс для учебного MVP. Приоритет — быстро получить работающий сквозной сценарий. Полнота документации, исчерпывающая обработка краёв и дублирующее тестирование откладываются до подготовки пилота.

## 1. Источники истины

| Артефакт | За что отвечает | Когда обновляется |
|---|---|---|
| `docs/PRODUCT.md` | Актуальное поведение и границы продукта | Меняется пользовательское поведение |
| `docs/ARCHITECTURE.md` | Актуальное устройство системы | Меняется межмодульное или труднообратимое решение |
| `docs/ROADMAP.md` | Очерёдность и единственный статус срезов | Меняется статус или точка продолжения |
| `docs/specs/NNNN-*.md` | Короткие правила сложного среза | До реализации; затем только при исправлении требования |
| `docs/adr/NNNN-*.md` | Причина труднообратимого решения | При принятии или замене решения |
| `api/openapi.yaml` | HTTP-контракт | Вместе с изменением endpoint |
| SQL-миграции | История схемы PostgreSQL | При изменении схемы |

Агент сначала использует roadmap, активный spec и поиск по релевантным разделам. Полные `PRODUCT.md` и `ARCHITECTURE.md` перечитываются только при противоречии или изменении их правил. Реализованное поведение не пересказывается одновременно в roadmap, spec и отчёте.

При конфликте продукт определяет поведение, архитектура — способ реализации. Существенное противоречие исправляется в обоих документах, а не маскируется кодом.

## 2. Единица работы

Единица работы — минимальный вертикальный срез, который даёт пользователю один работающий сценарий. Сначала реализуется happy path и необходимые для корректности инварианты. Необязательные варианты UX, polish, дополнительные edge cases и рефакторинг записываются в итоговом отчёте, но не добавляются в scope автоматически.

Следующий зависимый срез можно начать в той же сессии. Отдельная сессия на подготовку spec, его формальное принятие или handoff не требуется.

## 3. Feature-spec

Spec нужен только для неоднозначного поведения, нескольких связанных бизнес-правил, конкурентности/идемпотентности, нетривиальной миграции или breaking-контракта. Обычному CRUD, исправлению и локальному рефакторингу достаточно 3–7 критериев в задаче.

Spec должен быть коротким, обычно до 60 строк, и содержать:

- цель и границы;
- только новые бизнес-правила и инварианты;
- 3–7 проверяемых критериев;
- действительно блокирующие вопросы, если они есть.

Spec не повторяет схемы запросов из OpenAPI, актуальное устройство из `ARCHITECTURE.md`, общий Definition of Done или подробный план тестов. Номер равен максимальному существующему номеру плюс один; номера не резервируются.

Workflow-статус хранится только в `ROADMAP.md`: `Planned`, `In progress`, `Blocked`, `Done`. После создания короткого spec агент сразу ставит `In progress` и реализует его, если нет настоящего продуктового блокера.

Шаблон и список находятся в [specs/README.md](specs/README.md).

## 4. ADR

ADR нужен только для решения, которое дорого отменить, затрагивает несколько модулей или меняет базовую модель безопасности, данных либо развёртывания. Локальный выбор структуры, SQL-запроса, библиотеки или компонента ADR не требует.

Принятый ADR не переписывается задним числом. Заменяющее решение получает новый номер, а прежний ADR помечается `Superseded`.

## 5. OpenAPI

OpenAPI обновляется только вместе с фактическим изменением HTTP-контракта и проверяется валидатором. Spec не дублирует полные request/response schemas. Генерация клиентов и типов вводится только при реальной экономии ручной работы.

## 6. Быстрый цикл

Один главный агент выполняет весь цикл:

1. Проверяет `git status`, roadmap, активный spec и только релевантный код и документацию.
2. Фиксирует 3–7 критериев; для SPEC-0004–0006 создаёт короткий spec и без отдельного ожидания начинает реализацию.
3. Делает минимальный сквозной happy path без улучшений «заодно».
4. Каждый новый инвариант проверяет один раз на самом дешёвом подходящем уровне.
5. Запускает только проверки затронутой области, просматривает diff и исправляет найденные ошибки.
6. Обновляет реальный контракт и одну строку статуса roadmap. Подробную точку продолжения пишет только при незавершённой работе.

Субагенты и независимый review используются только по прямому запросу пользователя. Найденные необязательные улучшения не реализуются и не исследуются глубоко: достаточно коротко перечислить их в итоговом сообщении.

### Когда спрашивать пользователя

Вопрос нужен только когда выбор меняет продукт, расширяет MVP, требует нового труднообратимого решения, документы прямо противоречат друг другу или нужно внешнее/разрушительное действие. Обратимые технические решения агент принимает сам и выбирает самый простой вариант.

## 7. Demo Done для отдельного среза

Срез готов для продолжения MVP, когда:

- работают его критерии и основной пользовательский сценарий;
- бизнес-правила проверяются backend;
- запросы изолированы по `user_id`, а чужой ресурс выглядит отсутствующим;
- изменение схемы оформлено новой миграцией, которая применяется вперёд;
- транзакционные операции сохраняют необходимые данные атомарно;
- новый нетривиальный инвариант имеет один основной автоматический тест;
- изменённый HTTP-контракт отражён в OpenAPI;
- затронутые файлы отформатированы, компилируются и проходят целевые тесты;
- пропущенные проверки и известные ограничения названы в отчёте.

Для каждого среза по умолчанию не обязательны:

- одинаковые проверки правила на unit, repository, HTTP и E2E уровнях;
- E2E для каждого варианта, браузера или viewport;
- исчерпывающие loading, empty, validation, network error и retry состояния;
- полный локальный `make check`, production build и secret scan;
- migration `down/up`, полный integration suite и race detector;
- улучшение существующего кода или тестов вне критериев среза.

### Выбор уровня теста

- чистая доменная логика — unit-тест;
- SQL-инвариант, tenant isolation или транзакция — один PostgreSQL integration тест на новый риск;
- HTTP-код или сериализация — точечный HTTP-тест;
- React-поведение — точечный component-тест;
- E2E — один общий smoke-путь для крупного пользовательского потока, а не повторение всех правил нижних уровней.

Поведение тестируется на самом дешёвом достаточном уровне. Дублирование требует конкретного риска, а не делается по шаблону.

## 8. Проверки

Минимальная локальная проверка:

| Изменение | Что запускать |
|---|---|
| Документация | `git diff --check`, проверка изменённых ссылок |
| Go | `gofmt` и тест изменённого пакета без `-race` |
| TypeScript/React | formatter/typecheck затронутой области и целевой test file |
| HTTP | предыдущие проверки и OpenAPI validation |
| SQL/tenant/транзакция | применение миграции вперёд и один релевантный integration test |

Успешную проверку не повторяют, если влияющие на неё файлы не менялись. Полный набор `make check`, `make migrate-check`, `make test-integration` и `make test-e2e` запускается перед пилотом/релизом, при неисправном CI или по прямому запросу пользователя. Наличие этих команд не означает, что агент должен запускать их после каждого среза.

CI остаётся полной страховочной сеткой и может выполнять formatter, lint, typecheck, unit/component/integration/E2E, сборку, миграционный цикл, OpenAPI и secret scan. Локально дублировать весь CI не нужно.

## 9. Неизменяемые guardrails

- Не хранить и не логировать пароли, cookie, сырые session tokens и тексты карточек.
- Использовать параметризованный SQL и серверное UTC-время.
- Фильтровать пользовательские ресурсы по `user_id` на границе данных.
- Расписание вычисляет backend; ответ, позиция сессии и агрегаты меняются в одной транзакции.
- Не переписывать применённую миграцию без отдельного согласования.
- Не добавлять кэш, очередь, микросервис, универсальный framework или абстракцию «на будущее».
- Не смешивать изменение поведения с крупным механическим рефакторингом.

Процесс служит скорости MVP. Если документ, тест или улучшение не нужны для критерия, защиты данных пользователя либо продолжения следующего среза, их не следует создавать сейчас.
