# Процесс разработки Flashka

Этот документ задаёт лёгкий процесс агентной разработки. Его цель — сохранить
скорость небольшого проекта, но сделать требования, важные решения и критерии
готовности проверяемыми. Это не полноценный SDD-фреймворк.

## 1. Источники истины

| Артефакт | За что отвечает | Когда обновляется |
|---|---|---|
| `docs/PRODUCT.md` | Актуальное поведение и границы продукта | Меняется пользовательское поведение |
| `docs/ARCHITECTURE.md` | Актуальное устройство системы | Меняется техническая архитектура |
| `docs/ROADMAP.md` | Порядок MVP-срезов и текущая точка продолжения | В начале и конце рабочего этапа |
| `docs/specs/NNNN-*.md` | Контракт отдельного вертикального среза | До и во время реализации функции |
| `docs/adr/NNNN-*.md` | Почему принято труднообратимое решение | При принятии или замене решения |
| `api/openapi.yaml` | Исполняемый HTTP-контракт | Вместе с реализуемым endpoint |
| SQL-миграции | История схемы PostgreSQL | При каждом изменении схемы |
| `AGENTS.md` | Постоянные правила работы агентов | Когда меняется процесс или guardrail |

При конфликте сначала уточняется намерение, затем все затронутые актуальные
документы исправляются в одном изменении. ADR не является актуальной
спецификацией: это неизменяемая история причин и последствий.

## 2. Единица работы

Предпочтительная единица работы — небольшой вертикальный срез, который даёт
проверяемое поведение через все необходимые слои. Пример последовательности:

```text
регистрация и вход
        ↓
создание и просмотр карточки
        ↓
папки и перенос карточки
        ↓
создание учебной сессии
        ↓
ответ, прогресс и результат
```

Не следует без необходимости разносить по отдельным большим этапам всю схему
БД, весь backend и весь frontend. Срез может включать миграцию, HTTP-контракт,
backend, UI и тесты, оставаясь достаточно маленьким для одного содержательного
review.

## 3. Feature-spec

### Когда нужен

Feature-spec создаётся до реализации, если выполняется хотя бы одно условие:

- вводится новое неоднозначное пользовательское поведение или несколько
  связанных бизнес-правил;
- нужна миграция с нетривиальными инвариантами;
- появляется новая конкурентная или идемпотентная логика;
- меняется breaking product/API contract или требуется новый ADR;
- работа слишком широка, чтобы надёжно удерживать критерии в задаче.

Сам факт изменения frontend, backend и БД ещё не требует spec. Для обычного
CRUD, простого исправления, локального рефакторинга, текста интерфейса или
очевидного дополнительного поля достаточно 3–7 проверяемых критериев в задаче.

### Нумерация и имя

- Путь: `docs/specs/NNNN-short-kebab-name.md`.
- Заголовок: `SPEC-NNNN: Название`.
- Номера четырёхзначные, монотонные и никогда не переиспользуются.
- Следующий номер равен максимальному существующему номеру плюс один.
- Номер обозначает порядок появления, а не приоритет или этап разработки.
- Пустые номера заранее не резервируются.

Пример: `docs/specs/0001-authentication.md` с заголовком
`SPEC-0001: Регистрация и вход`.

Spec обязан фиксировать результат и проверяемые правила, но не пересказывать
построчно будущую реализацию. У каждого spec один статус:

- `Draft` — обсуждается, реализация не должна считаться утверждённой;
- `Accepted` — готов к реализации;
- `Implemented` — критерии выполнены и проверены;
- `Superseded` — заменён другим пронумерованным spec.

Перевод `Draft → Accepted` выполняет главный агент после собственной проверки
на противоречия и тестируемость. Отдельное подтверждение пользователя или
независимый review не требуются, если нет настоящего продуктового блокера.

Шаблон и реестр находятся в [specs/README.md](specs/README.md).

## 4. ADR

ADR создаётся, когда решение дорого отменить, влияет на несколько модулей,
ограничивает дальнейший дизайн или наверняка потребует объяснения «почему».
ADR не нужен для локального имени, обычной зависимости или реализации, прямо
следующей из принятой архитектуры.

- Путь: `docs/adr/NNNN-short-kebab-name.md`.
- Заголовок: `ADR-NNNN: Название`.
- Номер выдаётся по тем же правилам, что и для specs, но последовательности ADR
  и SPEC независимы.
- Принятый ADR не редактируется для изменения смысла. Новое решение создаёт
  новый ADR, а старый получает `Superseded by ADR-NNNN`.

Шаблон и реестр находятся в [adr/README.md](adr/README.md).

## 5. OpenAPI

`api/openapi.yaml` появляется вместе с первым реализуемым endpoint, а не как
пустая заготовка. После этого OpenAPI — обязательная часть каждого изменения
HTTP-контракта.

- Описываются фактически реализуемые запросы, ответы и общая модель ошибки.
- Спецификация проходит автоматическую валидацию в CI.
- TypeScript-типы или клиент желательно генерировать из контракта, когда это
  устранит ручное дублирование.
- Не следует заранее описывать весь предполагаемый API и создавать ложное
  ощущение реализованности.

## 6. Быстрый цикл Fast MVP

По умолчанию один главный агент выполняет весь цикл без ролевой оркестрации:

1. Проверяет `git status`, roadmap, активный spec и релевантные разделы
   источников истины.
2. Формулирует 3–7 проверяемых критериев в задаче или коротком spec.
3. Реализует минимальный целостный diff и не расширяет scope «на будущее».
4. Запускает проверки по риску, просматривает итоговый diff и исправляет
   обнаруженные проблемы.
5. Обновляет фактически затронутые контракты и статус roadmap; точку продолжения
   — только если оставляет работу незавершённой.
6. Для spec переводит статус в `Implemented`, обновляет реестр и сообщает итог.

Субагенты не используются для обычного разделения ролей. Допустим максимум один
сфокусированный read-only reviewer по прямому запросу пользователя либо когда
главный агент считает изменение высокорисковым, а независимая проверка стоит
дополнительных времени и токенов. Высокий риск: новая модель
auth/session/security, разрушительная или труднообратимая миграция, новая
конкурентная/идемпотентная логика, изменение алгоритма расписания, breaking
product/API contract или новый ADR. Уже принятый tenant-safe CRUD-паттерн сам по
себе не делает изменение высокорисковым.

Если несколько агентов всё же используются, они не редактируют одни файлы
одновременно. Главный агент проверяет их результат, фактический diff и команды;
отчёт субагента сам по себе не является доказательством готовности.

После `Implemented` отдельная новая сессия не обязательна. Агент может перейти к
следующему срезу, если он входит в текущий запрос пользователя.

### Когда допустим вопрос пользователю

Внутри фазы агент сначала разрешает неопределённость существующими требованиями
и минимальным scope. Остановиться и запросить решение пользователя нужно только
если:

- варианты существенно меняют пользовательское поведение;
- требуется расширить границы MVP;
- возникло новое труднообратимое решение без достаточных оснований;
- документы прямо противоречат друг другу;
- нужно разрешение на внешнее или потенциально разрушительное действие.

Имена пакетов, внутренние интерфейсы, детали SQL и другие обратимые технические
решения агент принимает самостоятельно.

Если работа не завершена за одну сессию, перед остановкой обновляется раздел
«Точка продолжения» в `ROADMAP.md`. Он должен содержать только проверяемое
состояние репозитория: выполненные пункты, результаты команд, известный блокер и
одно ближайшее действие. Пересказ разговора и скрытые предположения туда не
переносятся.

Если реализация обнаружила неверное требование, сначала исправляется spec и
связанные источники истины, затем код. Документация не подгоняется молча под уже
написанный код.

## 7. Definition of Done

Изменение считается готовым, когда применимые по риску пункты выполнены:

- критерии приёмки feature-spec или `PRODUCT.md` выполняются;
- бизнес-правила валидируются backend, а не только интерфейсом;
- схема поднимается миграциями на чистой PostgreSQL;
- миграция безопасна для принятой модели развёртывания;
- доменные правила покрыты unit-тестами;
- SQL-инварианты и tenant isolation покрыты интеграционными тестами;
- критический пользовательский путь покрыт или обновлён в E2E-тесте;
- UI обрабатывает loading, empty, validation и network error states;
- пройдены целевые formatter/lint/typecheck/tests для затронутой области;
- OpenAPI соответствует реализованному endpoint;
- логи не содержат пароль, cookie, сырой session token и тексты карточек;
- итоговый diff не содержит несвязанных изменений и необъяснённых временных
  обходов;
- актуальные документы обновлены в том же изменении;
- непройденная проверка явно указана в отчёте и не скрывается.

Покрытие тестами оценивается по риску и инвариантам, а не только по проценту
строк.

Минимальный локальный объём проверки:

| Изменение | Проверки |
|---|---|
| Документация и текст | `git diff --check`, ручная проверка изменённых ссылок |
| Обычный Go/TypeScript | formatter, lint/typecheck затронутой области, целевые тесты |
| HTTP-контракт | предыдущие проверки и OpenAPI validation |
| Миграция, SQL, tenant isolation | migration check и релевантные integration tests |
| Auth, расписание, транзакции, конкурентность, идемпотентность | релевантные integration tests и критический E2E |
| Релиз, отсутствие/неисправность CI или явный запрос | полный набор проектных команд |

Успешную проверку не повторяют после изменений, которые на неё не влияют.
В отчёте перечисляют выполненные проверки и осознанно пропущенные полные gates.
CI при этом сохраняет полный набор автоматических quality gates ниже.

## 8. Автоматические quality gates

По мере появления кода CI должен блокировать merge при ошибке хотя бы одной
применимой проверки:

### Backend

- `gofmt`/проверка чистого diff;
- `go vet`;
- unit и PostgreSQL integration tests;
- `go build`;
- применение всех миграций к чистой базе.

### Frontend

- formatter check;
- ESLint;
- TypeScript strict typecheck;
- unit/component tests;
- production build;
- Playwright для критического потока, когда он появится.

### Контракты и репозиторий

- валидация OpenAPI;
- проверка отсутствия секретов;
- `git diff --check` или эквивалентная whitespace-проверка.

Точные команды фиксируются в `Makefile`, package scripts и `AGENTS.md`, когда
инструменты реально добавлены. До этого нельзя выдумывать несуществующие команды.

## 9. Guardrails против лишней сложности

- HTTP handler не содержит бизнес-логику.
- React-компонент не вычисляет учебное расписание.
- Авторизация ресурса проверяется по `user_id` на границе данных.
- Repository не возвращает HTTP-типы.
- Пакет или файл `utils` не используется как свалка несвязанных функций.
- Go-интерфейс появляется на реальной границе либо для заменяемой зависимости в
  тесте, а не для каждой структуры.
- Новая внешняя зависимость должна давать понятную пользу, превышающую стоимость
  сопровождения.
- Изменение поведения не смешивается с крупным механическим рефакторингом.
- Кэш, очередь, микросервис или универсальный framework не добавляются «на
  будущее».

## 10. Что намеренно не вводится

- отдельный документ для каждой мелкой задачи;
- одноразовые plan-файлы в репозитории;
- ADR для каждого пакета или библиотеки;
- обязательные UML-диаграммы;
- полный API будущих версий до реализации;
- changelog до первого публичного релиза;
- метрика покрытия как самостоятельная цель;
- тяжёлое формальное согласование небольших изменений.

Процесс должен уменьшать неопределённость и риск. Если артефакт не помогает
принять решение, реализовать функцию или проверить результат, создавать его не
нужно.
