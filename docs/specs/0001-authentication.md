# SPEC-0001: Регистрация и вход

Status: Implemented  
Date: 2026-10-14

## Цель

Создать минимальный исполняемый каркас Flashka и дать пользователю личное
пространство с регистрацией, входом, выходом и восстановлением текущей
авторизации после перезагрузки страницы. Регистрация должна атомарно создавать
пользователя, его единственный системный корень `Inbox` и серверную сессию в
PostgreSQL.

Этот срез впервые вводит миграции, HTTP/OpenAPI-контракт, Go backend,
React/TypeScript frontend, локальное окружение и автоматические quality gates,
необходимые для последующих вертикальных срезов.

## Связанные требования и решения

- `PRODUCT.md`: `AUTH-01`–`AUTH-09`, `FOLDER-01`, критерии готовности MVP 1, 7–9;
- `ARCHITECTURE.md`: разделы 1–4, Auth из раздела 7, разделы 8–12;
- `ADR-0001`: модульный монолит;
- `ADR-0002`: непрозрачные серверные сессии в PostgreSQL.

## Входит в задачу

- каркас модульного Go-приложения и React/TypeScript frontend;
- конфигурация приложения, подключение к PostgreSQL и прямые/обратные SQL-
  миграции для данных этого среза;
- `users`, `auth_sessions` и минимально необходимая для `Inbox` таблица
  `folders` с архитектурными ограничениями владельца и системного корня;
- регистрация по логину и паролю с немедленной авторизацией;
- вход, получение текущего пользователя и выход из текущей сессии;
- защищённый frontend shell `/app`, публичные страницы `/login` и `/register`;
- единый JSON-формат API-ошибок, request ID, базовые security headers,
  same-origin/CSRF-проверка и ограничение частоты попыток входа;
- liveness/readiness endpoints, структурированные безопасные логи;
- OpenAPI-контракт реализованных API endpoints;
- воспроизводимые команды форматирования, lint/typecheck, тестов, сборки,
  проверки OpenAPI и миграций; CI запускает применимые команды.

## Не входит

- email, подтверждение аккаунта и восстановление пароля;
- изменение логина или пароля, удаление аккаунта, OAuth, MFA и управление
  списком сессий;
- принудительный выход на других устройствах или в других браузерных сессиях;
- пользовательские операции с папками и карточками, кроме автоматического
  создания `Inbox` при регистрации;
- учебные сессии и планировщик;
- Redis, внешний кэш, очередь, отдельный auth-сервис или обязательная фоновая
  очистка истёкших сессий;
- полноценное содержимое коллекции: `/app` в этом срезе является доступным
  только авторизованному пользователю shell для следующих фаз.

## Пользовательские сценарии и frontend UX

### Регистрация

1. Гость открывает `/register` и видит поля «Логин» и «Пароль», действие
   «Создать аккаунт», ссылку на вход и заметное предупреждение, что забытый
   пароль восстановить нельзя.
2. Клиент зеркально проверяет формат логина и длину пароля, но backend повторяет
   все проверки.
3. Во время отправки повторное нажатие заблокировано. Ошибки полей показываются
   рядом с полями, сетевая/неожиданная ошибка — в общей области; введённые
   значения не стираются.
4. После успеха пользователь уже авторизован и попадает на `/app`.

### Вход

1. Гость открывает `/login`, вводит логин и пароль и может перейти к регистрации.
2. Для неверного логина и неверного пароля UI показывает одно сообщение без
   раскрытия существования аккаунта.
3. После успеха пользователь попадает на `/app`.

### Восстановление и завершение сессии

- При открытии или перезагрузке `/app` frontend запрашивает текущего
  пользователя. До ответа показывается нейтральное loading-состояние без
  кратковременного показа приватного содержимого.
- При `401` защищённый маршрут заменяется переходом на `/login`.
- `/login` и `/register` при уже действующей сессии переводят на `/app`.
- Shell показывает сохранённое написание логина и действие «Выйти».
- После выхода cookie очищается, текущая строка сессии удалена, а frontend
  немедленно очищает auth/query state, передаёт same-origin событие через
  `BroadcastChannel` и переводит на `/login`. Другие открытые вкладки того же
  браузерного профиля обрабатывают событие без ожидания нового API-запроса.
  Повторная проверка `/auth/me` на `focus`/`visibilitychange` служит fallback
  для пропущенного события. Сессии других браузеров не затрагиваются.
- Loading, client validation, server validation, неверные credentials,
  rate-limit и network error имеют различимые состояния. Основной сценарий
  работает без горизонтальной прокрутки при ширине 360 px и на desktop;
  элементы управления имеют видимый focus и область не меньше 44×44 CSS px.

## Бизнес-правила и инварианты

### Логин и пароль

- Логин содержит от 3 до 32 ASCII-символов, соответствует
  `[A-Za-z0-9][A-Za-z0-9_-]{2,31}` и не обрезается автоматически.
- Для отображения хранится ровно принятое допустимое написание. Для поиска и
  уникальности хранится ASCII lowercase-вариант; `Alex` и `alex` конфликтуют.
- Пароль содержит от 8 до 128 Unicode code points. Backend считает декодированные
  UTF-8 runes, frontend использует эквивалентный `Array.from(value).length`;
  байты, UTF-16 code units и grapheme clusters длину не определяют. Пробелы,
  включая начальные и конечные, и combining sequences сохраняются;
  нормализация и обрезка не выполняются.
- Пароль никогда не сохраняется открытым текстом. В `users.password_hash`
  хранится только Argon2id PHC-строка с уникальной случайной солью 16 байт,
  результатом 32 байта и параметрами из валидированной конфигурации. Defaults:
  `m=19456 KiB`, `t=2`, `p=1`; startup отклоняет меньшие и некорректные значения.

### Регистрация и Inbox

- Создание `users`, корневой папки `Inbox` и `auth_sessions` происходит в одной
  транзакции. При любой ошибке не остаётся частично созданного аккаунта.
- У пользователя ровно один корень, это системная папка с `name = "Inbox"`,
  `name_normalized = "inbox"`, `is_inbox = true`, `parent_id = null`.
- Ограничения БД не допускают второй логин с тем же нормализованным значением,
  второй Inbox/корень одного пользователя, Inbox вне канонического корня,
  несистемный корень и связь папки с родителем другого пользователя.
- Конкурирующие регистрации вариантов одного логина дают ровно один успех;
  остальные получают безопасный конфликт логина без внутренних SQL-деталей.

### Серверная сессия

- В cookie находится ровно 32 байта из CSPRNG операционной системы, кодированные
  как base64url без padding. В БД хранится только SHA-256 декодированных байтов;
  сырой token существует только в cookie/памяти обработки запроса, не принимается
  из JSON и не логируется. Ошибка или short read RNG прерывает транзакцию.
- Срок сессии абсолютный и вычисляется от внедряемого серверного UTC clock по
  `SESSION_TTL`; default — 30 дней, допустимый диапазон startup-конфигурации —
  от 1 часа до 90 дней. Истёкшая или отсутствующая в БД сессия равна отсутствию
  авторизации. Продление срока при активности в этот срез не входит.
- Cookie имеет настроенное имя, `HttpOnly`, `SameSite=Lax`, `Path=/`; в
  production обязательно `Secure`. Установка и очистка cookie используют
  одинаковые name/path/security attributes.
- Logout идемпотентен для клиента: с действующей или уже отсутствующей cookie
  он очищает cookie и возвращает успех. Если token соответствует строке БД,
  удаляется только эта строка.
- `last_seen_at` может обновляться не чаще настроенного окна; default — 15 минут,
  допустимый диапазон — от 1 минуты до 24 часов. Обновление не влияет на
  абсолютный `expires_at`.

### Авторизация и защита запросов

- Единственный источник текущего пользователя — валидная неизтёкшая строка
  `auth_sessions`, найденная по хешу cookie. Доверять user ID от клиента нельзя.
- Все будущие приватные endpoints подключаются через общий auth middleware и
  дополнительно ограничивают данные по `user_id` в repository/SQL. В этом срезе
  это проверяется на `/auth/me` и shell.
- Единый CSRF middleware защищает register, login и logout до limiter, БД,
  мутации и установки cookie. Если есть `Origin`, он точно совпадает с
  нормализованным `TRUSTED_ORIGIN`; если есть `Sec-Fetch-Site`, допустимы только
  `same-origin` и `none`. `same-site`, `cross-site`, неизвестное значение,
  несовпадающий Origin или конфликт заголовков отклоняются. Отсутствие обоих
  заголовков также отклоняется, поэтому non-browser клиент передаёт доверенный
  Origin явно. Ответ — `403 csrf_rejected`. Изменение модели origin потребует
  отдельного CSRF-token до релиза.
- Login rate limiter использует `RemoteAddr` IP и нормализованный логин;
  forwarded IP headers игнорируются, так как trusted proxy configuration не
  входит в этот срез. Фиксированное in-process окно допускает пять неуспешных
  попыток на ключ за 15 минут; шестая и последующие до конца окна возвращают
  `429 login_rate_limited` с целочисленным `Retry-After`. Успешный вход очищает
  ключ. Неверные credentials учитываются, синтаксически невалидный запрос до
  limiter не доходит. Clock/store внедряемы; это защита одной реплики.
  Регистрация в этом срезе rate-limit не имеет.
- Каждая синтаксически валидная попытка входа, допущенная limiter, выполняет
  ровно один Argon2id verify. Несуществующий пользователь использует созданный
  при startup dummy PHC с теми же параметрами, существующий — реальный PHC.
  Неверный пароль и неизвестный логин имеют одинаковые status/code/message и
  форму тела. Повреждённый PHC существующего пользователя даёт нейтральный `500`.
- Пароль, password hash, cookie, сырой token и тела auth-запросов не попадают в
  логи и API-ответы. Все SQL-запросы параметризованы.

## Данные и миграции

### `users`

| Поле | Требование |
|---|---|
| `id` | UUID primary key |
| `login` | `varchar(32)`, исходное допустимое написание |
| `login_normalized` | `varchar(32)`, unique, ASCII lowercase |
| `password_hash` | `text`, Argon2id PHC string |
| `created_at`, `updated_at` | `timestamptz`, server UTC |

### `auth_sessions`

| Поле | Требование |
|---|---|
| `id` | UUID primary key |
| `token_hash` | `bytea`, unique, ровно 32 байта |
| `user_id` | UUID FK на `users`, `ON DELETE CASCADE` |
| `expires_at` | `timestamptz`, позже `created_at` |
| `created_at`, `last_seen_at` | `timestamptz`, server UTC |

Нужны индексы для поиска по `token_hash` и для ленивой очистки по
`expires_at`; unique index на token hash может одновременно обслуживать поиск.

### `folders`

В этом срезе таблица доступна только backend регистрации, но миграция создаёт
совместимую с целевой архитектурой основу: UUID `id`, `user_id`, nullable
`parent_id`, `name`, `name_normalized`, `is_inbox`, `created_at`, `updated_at`.
Уникальное ограничение `(user_id, id)` и составной self-reference
`(user_id, parent_id)` гарантируют одного владельца. Ограничения эквивалентны:

- `CHECK (NOT is_inbox OR (parent_id IS NULL AND name = 'Inbox' AND
  name_normalized = 'inbox'))`;
- `CHECK (parent_id IS NOT NULL OR is_inbox)`;
- `UNIQUE (user_id) WHERE parent_id IS NULL` и `UNIQUE (user_id) WHERE
  is_inbox`.

Они предотвращают некорректный или повторный корень; существование ровно одного
корня обеспечивает транзакция регистрации, потому что row-level constraint не
может потребовать дочернюю строку для каждого пользователя.

Миграции имеют явные `up` и `down`, применяются отдельной командой и
проверяются на чистой PostgreSQL полным циклом up/down/up. Уже применённые
миграции впоследствии не переписываются.

## HTTP API

Все API пути имеют префикс `/api/v1`, принимают и возвращают JSON UTF-8 с
`camelCase`. Ответ пользователя имеет только поля:

```json
{
  "user": {
    "id": "uuid",
    "login": "Alex"
  }
}
```

### `POST /api/v1/auth/register`

Запрос: `{"login":"Alex","password":"exact password"}`.

- `201 Created`: атомарно созданы пользователь, Inbox и сессия; установленная
  cookie; тело содержит пользователя;
- `400`: malformed JSON, неизвестные поля, неверный content type или тело больше
  фиксированного лимита auth-запроса 16 KiB;
- `409`: `login_taken` для занятого нормализованного логина, включая гонку;
- `422`: `validation_failed` с `fields.login` и/или `fields.password`;
- `500`: нейтральная внутренняя ошибка без частичных данных.

### `POST /api/v1/auth/login`

Запрос имеет ту же форму.

- `200 OK`: создана новая серверная сессия, установлена cookie, возвращён
  пользователь;
- `401`: единый `invalid_credentials` для неизвестного логина и неверного
  пароля;
- `400`, `422`, `429`, `500`: по общей модели. `429` имеет code
  `login_rate_limited` и `Retry-After`; ошибка формата логина может быть `422`,
  но не должна раскрывать существование пользователя.

Каждый успешный login создаёт отдельную сессию и не отзывает другие сессии.

### `POST /api/v1/auth/logout`

Тело отсутствует. Возвращает `204 No Content`, очищает cookie и удаляет текущую
сессию, если она существует. Endpoint допускает вызов с отсутствующей,
неизвестной или истёкшей cookie и остаётся идемпотентным. Same-origin-проверка
обязательна.

### `GET /api/v1/auth/me`

- `200 OK`: тело с текущим пользователем;
- `401`: `unauthenticated` при отсутствующей, неизвестной или истёкшей сессии;
- `500`: нейтральная внутренняя ошибка.

### Общая ошибка

```json
{
  "error": {
    "code": "validation_failed",
    "message": "Проверьте введённые данные",
    "fields": { "login": "Некорректный логин" },
    "requestId": "..."
  }
}
```

`fields` допускается только для ошибок полей и может отсутствовать. Сервер
генерирует UUID request ID и возвращает `X-Request-ID` на каждом API/health
ответе, включая `204` и `500`; в error body находится то же значение. Входящий
client request ID игнорируется. OpenAPI описывает схемы, `403 csrf_rejected`,
`429` и `Retry-After`, response headers и cookie security scheme.

Auth API и приватный shell возвращают `Cache-Control: no-store`. Все ответы
имеют `X-Content-Type-Options: nosniff` и `Referrer-Policy: no-referrer`; HTML
имеет ограничивающий CSP с `frame-ancestors 'none'` и Permissions Policy,
отключающей неиспользуемые возможности. Production HTTPS добавляет HSTS.
Permissive CORS headers не выдаются: frontend и API остаются same-origin.

Вне `/api/v1`: `GET /health/live` возвращает успех без зависимости от БД;
`GET /health/ready` возвращает успех только при готовом соединении с PostgreSQL.

## Ошибочные и граничные случаи

- Логины длиной 2/33, начинающиеся с `_`/`-`, содержащие Unicode, пробел или
  пунктуацию отклоняются; границы 3/32 и разрешённые `_`/`-` после первого
  символа принимаются.
- Регистр сохраняется для UI, но не позволяет дубликат и не влияет на вход.
- Пароли длиной 7/129 отклоняются; 8/128 принимаются; начальные/конечные пробелы
  сохраняются и нужны при следующем входе. Emoji вне BMP считается одним code
  point, а базовый символ с combining mark — двумя.
- Некорректный JSON, лишние поля, несколько JSON-значений и слишком большое
  тело не проходят до application service.
- Ошибка хеширования, генерации UUID/token, вставки Inbox или сессии откатывает
  регистрацию целиком.
- Два параллельных запроса регистрации одного нормализованного логина не дают
  `500` и не создают два аккаунта.
- Пустая, повреждённая, неизвестная и истёкшая cookie дают одинаковый `401` на
  `/auth/me`; истёкшая строка может удаляться лениво.
- Logout после logout успешен и не удаляет другие строки сессий пользователя.
- Матрица Origin/Fetch Metadata применяется к register, login и logout;
  отклонённый запрос не затрагивает limiter/БД и не устанавливает cookie.
- Недоступная БД делает readiness отрицательной и даёт безопасную API-ошибку;
  liveness остаётся положительной, пока HTTP-процесс работоспособен.
- Ошибка сети на формах сохраняет введённый логин и пароль в состоянии формы,
  но пароль не записывается в persistent browser storage.
- Если ответ регистрации потерян после commit, retry может получить
  `login_taken`: UI не изображает успех, сохраняет логин, не персистит пароль и
  предлагает перейти непосредственно на вход.

## Критерии приёмки

1. На чистой PostgreSQL миграции создают описанные таблицы и ограничения;
   up/down/up проходит автоматически.
2. Валидная регистрация возвращает `201`, создаёт ровно одного пользователя,
   ровно один Inbox и одну сессию в одной транзакции; password hash и token hash
   не совпадают с исходными секретами.
3. Повтор логина в другом регистре и параллельная регистрация дают безопасный
   `409`, не оставляя лишних Inbox или сессий.
4. Матрица границ логина и пароля, включая astral emoji и combining code points,
   одинаково проверяется backend и зеркально UI; пароль не trim/normalize.
5. После регистрации и после корректного входа `/auth/me` возвращает сохранённое
   написание логина при наличии cookie; после перезагрузки `/app` остаётся
   доступен.
6. Неизвестный логин и неверный пароль возвращают одинаковые
   status/code/message/body shape; instrumented verifier доказывает ровно один
   Argon2-вызов на каждую допущенную валидную попытку без wall-clock сравнения.
   Шестая неуспешная попытка в 15-минутном окне возвращает `429` с `Retry-After`.
7. Logout удаляет только текущую строку сессии, очищает cookie и делает эту
   cookie непригодной; повторный logout возвращает `204`, другая сессия того же
   пользователя остаётся действительной. Все вкладки текущего browser context
   сразу очищают приватное состояние и переходят на вход; focus fallback
   покрывает пропущенное событие.
8. `/app` недоступен гостю, не показывает приватный shell во время проверки и
   переводит на `/login` при `401`; публичные auth-страницы переводят
   авторизованного пользователя на `/app`.
9. Registration UI до отправки явно сообщает об отсутствии восстановления;
   формы имеют loading, validation, invalid-credentials, rate-limit и network
   error states без потери введённых данных.
10. Cookie и полная Origin/Fetch Metadata матрица соответствуют spec на всех
    mutating auth endpoints; отказ даёт фиксированный `403` до side effects.
    Cache/security headers соответствуют spec, permissive CORS отсутствует.
11. Логи успешных и ошибочных auth-запросов содержат request ID, метод, route,
    статус и длительность, но не содержат пароль, hash, cookie, сырой token или
    полное тело запроса.
12. OpenAPI соответствует четырём auth endpoints и общей модели ошибки;
    contract/integration tests проверяют основные успешные и ошибочные ответы.
13. `/health/live` и `/health/ready` различают работоспособность процесса и БД.
14. UI проходит критический E2E-путь: регистрация → `/app` → logout → login →
    `/app`, включая перезагрузку; layout проверен при 360 px и desktop без
    горизонтальной прокрутки.
15. Все зафиксированные в репозитории formatter, lint, vet, typecheck, unit,
    PostgreSQL integration, E2E, OpenAPI validation и production build команды
    проходят локально и в CI; секреты и сгенерированные артефакты не закоммичены.

## План тестирования

### Unit

- таблица допустимых/недопустимых логинов и паролей, сохранение регистра и
  отсутствие trim пароля;
- Argon2id defaults/startup validation, hash/verify, неверный пароль и malformed
  PHC string;
- генерация token и детерминированный SHA-256 hash без сохранения сырого token;
- expiry через внедряемый clock, cookie attributes, полная origin/fetch-site
  матрица;
- limiter через внедряемые clock и хранилище;
- frontend validation, состояния форм и auth route guards.

### PostgreSQL integration и HTTP contract

- миграции up/down/up на чистой БД и фактические schema constraints;
- атомарность user + Inbox + session, case-insensitive uniqueness и
  конкурентная регистрация;
- попытки нарушить каждый root/Inbox check, partial unique index и cross-user
  parent FK;
- успешные register/login/me/logout, expiry, повторный logout и изоляция двух
  сессий;
- одинаковый публичный результат и ровно один verifier call для неверных
  credentials;
- rollback при принудительной ошибке внутри регистрации;
- OpenAPI validation и проверка реализованных response status/body/cookie.

### E2E и эксплуатационные проверки

- браузерный путь registration → reload → logout → login на чистой БД,
  включая немедленный logout в двух pages одного browser context и focus fallback;
- редиректы гостя и авторизованного пользователя, недоступная сеть и validation;
- viewport 360 px и desktop, клавиатурный focus и отсутствие горизонтального
  overflow;
- readiness при доступной/недоступной БД, production build, запуск binary со
  встроенным или согласованно раздаваемым frontend;
- автоматическая проверка логов на отсутствие известных тестовых секретов.

## Нерешённые вопросы

Отсутствуют. Security defaults и диапазоны их валидации закреплены этим spec;
увеличение Argon2id work factors после benchmark целевого окружения допустимо
при сохранении принятого минимума.
