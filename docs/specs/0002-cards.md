# SPEC-0002: Карточки

Date: 2026-10-15

## Цель

Дать авторизованному пользователю минимальный законченный сценарий карточек: быстро сохранить две текстовые стороны в `Inbox`, увидеть список, открыть, изменить и безвозвратно удалить карточку.

Связанные требования: `CARD-01`–`CARD-03`, `CARD-05`–`CARD-09`, `AUTH-09`. Основа: `SPEC-0001`, разделы 4, 7–9 и 12 `ARCHITECTURE.md`, ADR-0001 и ADR-0002.

## Входит в задачу

- новая миграция `cards` с агрегатами будущего расписания;
- защищённый CRUD API и OpenAPI-контракт;
- список карточек непосредственно в `Inbox`, detail и формы создания/редактирования;
- подтверждение удаления, loading/empty/validation/network-error состояния;
- адаптивный основной путь и риск-ориентированные backend/frontend/E2E-тесты.

## Не входит

- выбор другой папки при создании, дерево папок и перенос карточки — SPEC-0003;
- поиск, теги, дубликаты, массовые операции, импорт/экспорт и форматирование;
- статусы прогресса в UI, учебные сессии и изменение агрегатов расписания;
- soft delete и восстановление удалённой карточки.

## Пользовательский сценарий и UX

- `/app` показывает карточки `Inbox` и основное действие «Добавить карточку». Сначала виден skeleton/нейтральный loading, пустой список объясняет, как создать первую карточку, а ошибка загрузки предлагает «Повторить».
- `/app/cards/new` содержит только `front` и `back`. После `201` показывается подтверждение и доступны «Добавить ещё» (очищает форму и оставляет её в фокусе) и переход к созданной карточке. Повторный submit во время запроса заблокирован.
- `/app/cards/:id` показывает обе стороны как обычный текст, позволяет перейти к редактированию, сохранить изменения и удалить карточку.
- Удаление требует явного подтверждения с предупреждением о необратимости. После `204` пользователь возвращается к списку; отмена ничего не меняет.
- Detail и формы различают загрузку, `404`, field validation и network/server error; при ошибке введённые значения сохраняются и действие можно повторить.
- Основной сценарий работает без горизонтальной прокрутки при 360 px, имеет видимый focus, подписанные элементы управления и цели нажатия не меньше 44×44 CSS px. Многострочный текст переносится и не исполняется как разметка.

## Бизнес-правила и инварианты

- `front` и `back` обязательны. Backend удаляет с краёв символы со свойством Unicode `White_Space` (`strings.TrimFunc(value, unicode.IsSpace)`), затем принимает 1–2000 Unicode code points. Frontend зеркалит именно это множество через Unicode property escape `\p{White_Space}`, но backend остаётся источником истины. Внутренние пробелы и переводы строк сохраняются.
- Хранится обрезанное значение. Одинаковые карточки допустимы.
- Создание в этом срезе всегда использует единственный `Inbox` текущего пользователя; клиент не передаёт и не выбирает `folderId`.
- Все чтения и мутации ограничены `user_id` из серверной сессии. Чужой, отсутствующий и уже удалённый `cardId` дают одинаковый `404 card_not_found`.
- Счётчики новой карточки равны нулю, а `intervalDays`, `lastReviewedAt` и `dueAt` равны `null`. CRUD текста их не изменяет.
- `createdAt` неизменно; успешный PATCH меняет `updatedAt` по внедряемому серверному UTC clock. UUID и время не принимаются от клиента.
- Тексты карточек, request body и их производные не записываются в логи.
- Изменяющие запросы проходят существующую CSRF-защиту; все endpoints требуют действующую серверную сессию.

## Данные и миграция

Новая, не переписывающая `000001`, миграция создаёт `cards` в соответствии с `ARCHITECTURE.md`: UUID `id`, `user_id`, `folder_id`, `front`, `back`, `correct_count`, `incorrect_count`, `correct_streak`, nullable `interval_days`, `last_reviewed_at`, `due_at`, `created_at`, `updated_at`.

Обязательны:

- FK `user_id -> users(id) ON DELETE CASCADE` и составной FK `(user_id, folder_id) -> folders(user_id, id)`;
- неотрицательные счётчики, `correct_streak <= correct_count`, непустые строки не длиннее 2000 символов и `updated_at >= created_at`;
- при `correct_count + incorrect_count = 0` все `interval_days`, `last_reviewed_at`, `due_at` равны `NULL`; после первого ответа все три поля не `NULL`. SPEC-0002 создаёт только первое состояние, а будущий study-срез обязан переводить агрегаты во второе атомарно;
- уникальность `(user_id, id)` для будущих tenant-safe связей;
- индексы `(user_id, folder_id, created_at DESC, id DESC)` и `(user_id, due_at)`.

Down удаляет только объекты этой миграции. Полный `up/down/up` должен проходить на чистой PostgreSQL и поверх SPEC-0001.

## HTTP API

JSON использует `camelCase`, время — RFC 3339. Неизвестные поля и лишний JSON отклоняются как `400 invalid_request`. Лимит тела обязан пропускать любые валидные `front`/`back`. Ошибки имеют общую форму из `ARCHITECTURE.md`.

### `GET /api/v1/cards?folderId=&cursor=&limit=`

В SPEC-0002 `folderId` опускается, и сервер выбирает `Inbox`; переданный `folderId` отклоняется как `422 validation_failed` до SPEC-0003. `limit` по умолчанию 50, диапазон 1–100. Стабильный порядок: `createdAt DESC, id DESC`. `cursor` — versioned base64url JSON с `createdAt`, `id` и `userId`, без срока действия и без нового секрета. `userId` обязан совпасть с серверной сессией; malformed payload, неизвестная версия и owner mismatch дают `400 invalid_cursor`. SQL независимо всегда фильтрует по session `user_id`.

`200`: `{ "items": [CardSummary...], "nextCursor": string | null }`. `CardSummary`: `id`, `front`, `back`, `createdAt`, `updatedAt`. Клиент показывает «Загрузить ещё», пока `nextCursor` не равен `null`, не теряя уже загруженные элементы при retry.

### `POST /api/v1/cards`

Запрос: `{ "front": string, "back": string }`.

`201`: `{ "card": Card }`, где `Card` дополнительно содержит `folderId`, нулевые `correctCount`, `incorrectCount`, `correctStreak` и nullable `intervalDays`, `lastReviewedAt`, `dueAt`. Возможны `422 validation_failed` с `fields.front`/`fields.back`, `401`, `403 csrf_rejected` и общая `500`.

### `GET /api/v1/cards/{cardId}`

`200`: `{ "card": Card }`; невалидный UUID, отсутствующая или чужая карточка — `404 card_not_found` без раскрытия владельца.

### `PATCH /api/v1/cards/{cardId}`

Запрос содержит `front` и/или `back`; хотя бы одно поле обязательно. В этом срезе `folderId` не принимается. `200`: `{ "card": Card }`. Помимо общих ошибок возможны `422 validation_failed` и tenant-safe `404 card_not_found`.

### `DELETE /api/v1/cards/{cardId}`

Успех: `204` без тела. Повторное удаление и чужой ID возвращают tenant-safe `404 card_not_found`.

## Ошибочные и граничные случаи

- whitespace-only, 2001 code point и отсутствующее обязательное поле дают field error; ровно 2000 code points, NBSP/EM SPACE по краям, astral emoji, combining sequence и внутренние переносы проверяются явно;
- malformed, unsupported-version и owner-mismatch cursor дают `400 invalid_cursor`, не `500`; валидный cursor не истекает;
- параллельные edit/delete дают один допустимый итог: операция, не нашедшая строку текущего пользователя, получает `404`; частичного обновления нет;
- исчезновение карточки между открытием и сохранением/удалением показывает `404` и безопасный переход к списку;
- общий обработчик `401` очищает auth state и переводит на `/login`;
- тексты с HTML/скриптами отображаются React как текст.

## Критерии приёмки

1. После регистрации пользователь создаёт карточку двумя полями; она сохраняется в его `Inbox`, видна в списке и доступна по прямому URL после reload.
2. Обе стороны проходят одинаковую серверную Unicode-валидацию и сохраняют внутренние whitespace/переводы строк; дубликаты разрешены.
3. Пользователь изменяет одну или обе стороны без изменения папки и агрегатов.
4. Удаление невозможно без подтверждения в UI и после успеха карточка больше не читается и не появляется в списке.
5. Пользователь A не может перечислить, прочитать, изменить или удалить карточку пользователя B; ответы не раскрывают её существование.
6. Список имеет стабильную cursor-пагинацию и корректные loading, empty, retry и load-more состояния.
7. OpenAPI, миграции, backend и frontend реализуют один контракт; логи не содержат тексты карточек.
8. Основной путь доступен на desktop и при ширине 360 px.

## План тестирования

- **Unit:** trim/count Unicode, границы 0/1/2000/2001, сохранение внутренних пробелов, PATCH хотя бы с одним полем, cursor encode/decode.
- **PostgreSQL integration:** defaults/checks/FK, составная tenant-связь с папкой, сортировка и границы страниц, CRUD с обязательным `user_id`, полный migration `up/down/up`.
- **HTTP integration:** cookie auth и CSRF, строгий JSON, коды/формы ответов, field errors, `401`, tenant-safe `404`, cursor errors; лог-capture подтверждает отсутствие текстов карточек.
- **Frontend component:** формы и Unicode validation, loading/empty/error/retry, сохранение ввода на ошибке, confirm/cancel удаления и безопасный вывод текста.
- **E2E:** регистрация → создание → список → detail/reload → редактирование → подтверждённое удаление; desktop и один критический проход при 360 px.

Применимые `make fmt-check`, `make lint`, `make test`, `make test-integration`, `make migrate-check`, `make openapi-check`, `make secret-check`, `make build` и `make test-e2e` должны пройти.

## Нерешённые вопросы

Блокирующих вопросов нет. Выбор/перенос в другие папки намеренно отложен до SPEC-0003; расширение тех же endpoints не должно менять поведение Inbox по умолчанию.
