# Архитектура Flashka

Статус: целевая архитектура MVP.  
Связанная спецификация: [PRODUCT.md](PRODUCT.md).

Процесс изменения архитектуры описан в [DEVELOPMENT.md](DEVELOPMENT.md).
Обоснования исходных решений зафиксированы в ADR:

- [ADR-0001: Модульный монолит](adr/0001-modular-monolith.md);
- [ADR-0002: Сессии аутентификации в PostgreSQL](adr/0002-postgresql-auth-sessions.md);
- [ADR-0003: Бинарный планировщик повторений MVP](adr/0003-mvp-review-scheduler.md).

## 1. Архитектурные решения

Flashka реализуется как модульный монолит:

```text
Browser (React/TypeScript)
          |
       HTTPS / JSON
          |
Go HTTP API + static frontend
          |
      PostgreSQL
```

Такой вариант соответствует масштабу MVP, даёт атомарные транзакции для
учебного прогресса и не требует распределённой инфраструктуры. Границы модулей
сохраняются в коде, но развёртывается один backend-процесс и одна база данных.

Зафиксированные ограничения:

- Redis и любой внешний кэш не используются;
- PostgreSQL — единственное персистентное хранилище, включая пользовательские
  сессии;
- frontend не обращается к базе и не вычисляет учебное расписание;
- фоновые очереди и обязательные cron-задачи отсутствуют;
- API не обязан быть публично совместимым до выхода MVP, но изменения схемы
  оформляются миграциями.

## 2. Технологический стек

Версии фиксируются при начале реализации на последних поддерживаемых стабильных
релизах и затем закрепляются в `go.mod` и lock-файле frontend.

### Backend

- Go;
- стандартный `net/http` и лёгкий маршрутизатор `chi`;
- PostgreSQL-драйвер и пул `pgx`;
- SQL-миграции (`golang-migrate` или эквивалентный CLI);
- явный SQL, при необходимости типобезопасная генерация через `sqlc`; тяжёлый
  ORM не нужен;
- структурированные логи `log/slog`;
- хеширование пароля Argon2id из `golang.org/x/crypto`.

### Frontend

- React + TypeScript;
- Vite;
- React Router;
- TanStack Query для серверного состояния;
- React Hook Form + Zod для форм и зеркальной клиентской валидации;
- CSS Modules или единый набор CSS custom properties; UI-фреймворк не обязателен;
- Vitest + Testing Library, Playwright для критических end-to-end сценариев.

Backend всё равно повторяет всю валидацию: данные от браузера недоверенные.

## 3. Модули backend

```text
auth       регистрация, вход, выход, проверка сессии
users      пользователь и правила логина
folders    дерево папок и системный Inbox
cards      CRUD карточек и перенос между папками
study      формирование раунда, ответы, расписание и результат
platform   HTTP, конфигурация, БД, миграции, логирование, ошибки
```

Рекомендуемый поток зависимости внутри каждого модуля:

```text
HTTP handler -> application service -> repository -> PostgreSQL
                         |
                    domain rules
```

HTTP-структуры не передаются напрямую в репозитории. Доменные правила, особенно
планировщик и операции с деревом, тестируются без HTTP. Между модулями допустимы
явные интерфейсы/сервисы, но не циклические импорты.

## 4. Модель данных

Все идентификаторы — UUID, время — `timestamptz` в UTC. Для изменяемых сущностей
есть `created_at` и `updated_at`. Названия ниже задают смысл, а не окончательный
синтаксис миграций.

### `users`

| Поле | Тип | Правило |
|---|---|---|
| `id` | uuid PK | генерируется сервером/БД |
| `login` | varchar(32) | исходное написание для UI |
| `login_normalized` | varchar(32) | lowercase, UNIQUE |
| `password_hash` | text | только Argon2id PHC string |
| `created_at`, `updated_at` | timestamptz | UTC |

### `auth_sessions`

| Поле | Тип | Правило |
|---|---|---|
| `id` | uuid PK | внутренний ID |
| `token_hash` | bytea UNIQUE | SHA-256 случайного токена; сырой токен только cookie |
| `user_id` | uuid FK | `users`, cascade delete |
| `expires_at` | timestamptz | абсолютное время окончания |
| `created_at`, `last_seen_at` | timestamptz | `last_seen_at` обновляется не чаще заданного окна |

Cookie содержит непрозрачный криптографически случайный токен. Хранить сырой
токен в БД нельзя. Истёкшие строки можно лениво удалять при входе/проверке;
отдельный worker для корректности не нужен.

### `folders`

| Поле | Тип | Правило |
|---|---|---|
| `id` | uuid PK | |
| `user_id` | uuid FK | `users`, cascade delete |
| `parent_id` | uuid nullable FK | родитель того же пользователя |
| `name` | varchar(80) | отображаемое имя |
| `name_normalized` | varchar(80) | lowercase для уникальности |
| `is_inbox` | boolean | системный корень |
| `created_at`, `updated_at` | timestamptz | |

Ограничения/индексы:

- один `is_inbox = true` на пользователя (partial unique index);
- один корень на пользователя; для MVP это `Inbox`;
- уникальный `name_normalized` среди детей одного родителя;
- индекс `(user_id, parent_id)`;
- составной уникальный ключ `(user_id, id)` позволяет составным внешним ключом
  гарантировать, что родитель принадлежит тому же пользователю;
- цикл и глубина проверяются сервисом в транзакции через recursive CTE.

### `cards`

| Поле | Тип | Правило |
|---|---|---|
| `id` | uuid PK | |
| `user_id` | uuid FK | владелец |
| `folder_id` | uuid FK | папка того же владельца, обязательно |
| `front`, `back` | varchar(2000) | непустой обычный текст |
| `correct_count` | integer | `>= 0` |
| `incorrect_count` | integer | `>= 0` |
| `correct_streak` | integer | `>= 0` |
| `interval_days` | integer nullable | null до первого ответа |
| `last_reviewed_at` | timestamptz nullable | |
| `due_at` | timestamptz nullable | null означает новую карточку |
| `created_at`, `updated_at` | timestamptz | |

Индексы: `(user_id, folder_id)`, `(user_id, due_at)`. Внешний ключ
`(user_id, folder_id)` не позволяет связать карточку с чужой папкой.

Агрегаты расписания хранятся на карточке ради простых запросов, но каждый их
переход подтверждается неизменяемым `review_events`.

### `study_sessions`

| Поле | Тип | Правило |
|---|---|---|
| `id` | uuid PK | |
| `user_id` | uuid FK | владелец |
| `scope_type` | enum/text | `all` или `folder` |
| `scope_folder_id` | uuid nullable FK | обязателен только для `folder` |
| `requested_count` | smallint | 1–100 |
| `actual_count` | smallint | зафиксировано при старте |
| `status` | enum/text | `active`, `completed`, `abandoned` |
| `created_at`, `completed_at` | timestamptz | |

Сессия хранит исходную область для повторного старта, но удаление/перемещение
папки после создания не меняет состав.

### `study_session_cards`

| Поле | Тип | Правило |
|---|---|---|
| `session_id` | uuid FK | часть PK |
| `card_id` | uuid FK nullable | null после удаления карточки |
| `position` | smallint | часть PK, 1..N |
| `selection_bucket` | enum/text | `due`, `new`, `early` |
| `revealed_at` | timestamptz nullable | оборот был открыт |
| `result` | enum/text nullable | `correct` или `incorrect` |
| `answered_at` | timestamptz nullable | |

Уникальность `(session_id, card_id)` не допускает повтор карточки. Результат
может появиться только после `revealed_at`; это проверяют сервис и ограничение
БД. Для простоты удаления FK карточки использует `ON DELETE SET NULL`.

### `review_events`

| Поле | Тип | Правило |
|---|---|---|
| `id` | uuid PK | |
| `user_id` | uuid FK | владелец |
| `session_id` | uuid FK | источник ответа |
| `card_id` | uuid nullable FK | `SET NULL` при удалении |
| `rating` | enum/text | `correct` или `incorrect` |
| `reviewed_early` | boolean | карточка ещё не была назначена |
| `previous_interval_days` | integer nullable | снимок до ответа |
| `next_interval_days` | integer | результат планировщика |
| `previous_due_at`, `next_due_at` | timestamptz nullable | аудит перехода |
| `created_at` | timestamptz | время ответа |

Уникальность `(session_id, card_id)` обеспечивает идемпотентность ответа на
уровне БД. События не редактируются.

## 5. Дерево папок

Adjacency list (`parent_id`) достаточен для ограниченной глубины и PostgreSQL.
Потомки области выбираются recursive CTE с обязательным `user_id`. Перемещение
папки выполняется транзакционно:

1. заблокировать перемещаемую папку;
2. проверить владельца и запрет для `Inbox`;
3. получить цепочку/поддерево через recursive CTE;
4. отклонить нового родителя, если это сама папка, её потомок или создаётся
   глубина больше 10;
5. проверить уникальность имени среди новых соседей;
6. обновить `parent_id`.

Пагинация дерева в MVP не нужна. Список карточек папки пагинируется cursor-based;
для первого релиза допустим стабильный курсор `(created_at, id)` и лимит до 100.
Frontend проецирует технический корень отдельно: `Inbox` и его непосредственные
дочерние узлы отображаются на одном верхнем уровне, отступ начинается с более
глубоких подпапок, а breadcrumb пользовательской папки исключает `Inbox`. API и
`parent_id` при этом не меняются.

## 6. Планировщик и создание сессии

Чистая функция планировщика получает текущее состояние карточки, бинарную оценку
и серверное `now`, возвращает новое состояние. Лестница:

```text
success intervals: 1 -> 3 -> 7 -> 14 -> 30 -> 60 -> 120 days
incorrect: interval = 1 day, correct_streak = 0
```

Точные продуктовые правила находятся в разделе 8 `PRODUCT.md`; архитектурный
код не должен дублировать их несколькими реализациями.

Создание сессии выполняется на сервере:

1. проверить область и её принадлежность пользователю;
2. получить ID папок области recursive CTE;
3. выбрать до N карточек: `due`, затем `new`, затем `early`, с заявленным
   порядком; случайность реализовать средствами PostgreSQL только на ограниченном
   наборе кандидатов либо стабильным серверным tie-break, чтобы не делать
   полный `ORDER BY random()` на растущей таблице;
4. создать `study_sessions` и позиции `study_session_cards` в одной транзакции;
5. вернуть первую позицию и сводку.

В MVP ожидается умеренный объём коллекции. Перед усложнением отбора нужны
измерения, а не преждевременный кэш.

### Атомарная запись ответа

В транзакции:

1. найти сессию и позицию по `user_id`, заблокировать строку карточки `FOR UPDATE`;
2. убедиться, что сессия активна, оборот открыт и результата ещё нет;
3. вычислить следующее состояние один раз;
4. вставить `review_events`, записать результат позиции, обновить агрегаты карточки;
5. если отвечены все позиции, пометить сессию завершённой;
6. commit и вернуть следующую карточку или итог.

Повтор идентичного запроса возвращает уже сохранённый результат без нового
события. Конфликтующий повтор получает `409 Conflict`.

## 7. HTTP API

Префикс: `/api/v1`. Формат: JSON, UTF-8. Имена полей — `camelCase`, время —
RFC 3339. Успешное удаление возвращает `204`. Списки возвращают объект с `items`,
а не голый массив.

### Auth

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/auth/register` | создать пользователя, Inbox и сессию |
| `POST` | `/auth/login` | начать сессию |
| `POST` | `/auth/logout` | удалить текущую сессию |
| `GET` | `/auth/me` | текущий пользователь |

### Folders and cards

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/folders/tree` | полное дерево со счётчиками |
| `POST` | `/folders` | создать папку |
| `PATCH` | `/folders/{folderId}` | переименовать/переместить |
| `DELETE` | `/folders/{folderId}` | удалить пустую папку |
| `GET` | `/cards?folderId=&cursor=&limit=` | карточки непосредственно в папке |
| `POST` | `/cards` | создать; без `folderId` — в Inbox |
| `GET` | `/cards/{cardId}` | получить карточку и прогресс |
| `PATCH` | `/cards/{cardId}` | изменить текст/папку |
| `DELETE` | `/cards/{cardId}` | удалить карточку |

### Study

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/study/preview?scopeType=&folderId=` | доступные количества по статусам |
| `POST` | `/study/sessions` | создать фиксированный раунд |
| `GET` | `/study/sessions/active` | незавершённая сессия или `204` |
| `GET` | `/study/sessions/{sessionId}` | состояние и текущая позиция |
| `POST` | `/study/sessions/{sessionId}/cards/{position}/reveal` | отметить открытие оборота |
| `PUT` | `/study/sessions/{sessionId}/cards/{position}/answer` | идемпотентно записать оценку |
| `POST` | `/study/sessions/{sessionId}/abandon` | завершить досрочно |
| `GET` | `/study/sessions/{sessionId}/result` | итог и ошибки |

`PUT answer` выбран намеренно: ресурс результата позиции имеет одно итоговое
значение. Клиент дополнительно отправляет уникальный `requestId`; сервер может
логировать его, но корректность обеспечивают ограничения БД.

### Ошибки

Единая форма:

```json
{
  "error": {
    "code": "folder_not_empty",
    "message": "Папка не пуста",
    "fields": { "name": "Название уже используется" },
    "requestId": "..."
  }
}
```

Ожидаемые статусы: `400` неверный JSON, `401` нет сессии, `403` для запрещённого
системного действия, `404` в том числе для чужого ресурса, `409` конфликт
состояния/уникальности, `422` ошибки полей, `429` ограничение частоты, `500`
неожиданная ошибка. Внутренние подробности и SQL не возвращаются.

## 8. Аутентификация и безопасность

- пароль хешируется Argon2id с солью и параметрами, выбранными по актуальной
  рекомендации OWASP для доступной инфраструктуры; PHC-строка хранит параметры;
- сырой пароль и session token не попадают в логи;
- cookie: `HttpOnly`, `Secure` в production, `SameSite=Lax`, ограниченный `Path`,
  разумный срок (например, 30 дней);
- frontend и API развёртываются на одном origin. Для изменяющих запросов
  дополнительно проверяются `Origin`/`Sec-Fetch-Site`; если архитектура origin
  изменится, до релиза добавляется CSRF-token;
- вход ограничивается по комбинации IP и нормализованного логина. Без Redis
  допустим in-process limiter как защита от всплесков; он не считается строгой
  распределённой гарантией. В нескольких репликах нужен PostgreSQL-backed либо
  edge rate limit;
- сравнение хешей и обработка несуществующего логина не должны создавать явный
  timing/user-enumeration канал;
- запросы используют параметры, текст отображается React как текст, CSP и
  стандартные security headers включены;
- CORS в production не разрешает произвольные origins;
- авторизация проверяется в SQL/репозитории по `user_id`, а не только middleware;
- секреты приходят через окружение/secret store и не коммитятся;
- все HTTP-серверные timeout'ы и лимит тела запроса заданы явно.

Отсутствие восстановления пароля — осознанное продуктовое ограничение, которое
должно быть явно показано до создания аккаунта.

## 9. Frontend-архитектура

Рекомендуемые feature-модули:

```text
app/          router, providers, layout, error boundary
features/
  auth/
  cards/
  folders/
  study/
pages/
shared/       API client, UI primitives, hooks, styles, types
```

- TanStack Query хранит серверное состояние; глобальный store не добавляется,
  пока нет подтверждённого сценария.
- Локальное состояние формы/анимации остаётся в компоненте.
- После входа и при открытии `/login` авторизованным пользователем frontend
  переходит на `/app` (Inbox), без запроса активной учебной сессии. Активная
  сессия загружается по действию «Учиться» через `/app/study/active`.
- API-клиент всегда отправляет cookie, распознаёт общую форму ошибки и на `401`
  переводит пользователя на вход.
- Оптимистические обновления допустимы для переименования/переноса, если есть
  rollback. Ответ в учебной сессии показывается как сохранённый только после
  подтверждения сервера; на ошибке доступны безопасный повтор и тот же текст.
- Жест свайпа — дополнительный adapter над тем же действием, что и кнопка, а не
  отдельная бизнес-логика.
- Первое нажатие по учебной карточке вызывает существующий серверный reveal;
  после него повторные нажатия переключают видимую сторону локально, не меняя
  состояние учебной сессии.
- Состояние свёрнутых веток дерева папок локально для UI: кнопка стрелки/иконки
  управляет веткой независимо от кнопки выбора папки и не вызывает API-запрос.
- Drag-and-drop папок — дополнительный UI-adapter над существующим
  `PATCH /folders/{folderId}` с `parentId`. UI заранее исключает очевидные
  недопустимые цели и после подтверждённого ответа перечитывает дерево; сервер
  остаётся источником проверок владельца, цикла, глубины и уникальности имени.
- Мобильный drawer папок открывается глобальным touch-жестом вправо из любой
  области страницы; порог и проверка направления защищают вертикальную прокрутку
  от ложного срабатывания, а при открытом drawer слушатель отключён.
- Маршруты минимум: `/login`, `/register`, `/app`, `/app/cards/new`,
  `/app/cards/:id`, `/app/study/new`, `/app/study/:id`,
  `/app/study/:id/result`.

## 10. Конфигурация и развёртывание

Минимальные переменные окружения:

```text
APP_ENV
HTTP_ADDR
DATABASE_URL
SESSION_COOKIE_NAME
SESSION_TTL
ARGON2_MEMORY
ARGON2_ITERATIONS
ARGON2_PARALLELISM
TRUSTED_ORIGIN
LOG_LEVEL
```

Один production artifact может содержать собранный frontend и Go binary либо
они могут раздаваться отдельно с одного origin. Для MVP предпочтителен один
контейнер приложения плюс управляемый PostgreSQL. Перед готовностью приложение
проверяет соединение с БД; readiness не должна быть успешной без БД.

Миграции запускаются отдельной release-командой перед новой версией, а не
самовольно каждой репликой. Изменения схемы вперёд совместимы на время
развёртывания. Резервное копирование PostgreSQL и проверка восстановления —
обязательство окружения production.

## 11. Наблюдаемость

- JSON-логи с `requestId`, методом, шаблоном маршрута, статусом, длительностью и
  `userId` после авторизации; без содержимого карточек, пароля и cookie;
- метрики: количество/длительность HTTP-запросов, ошибки по коду, активные
  соединения БД, регистрации, созданные карточки, начатые/завершённые сессии;
- `/health/live` не зависит от БД, `/health/ready` проверяет готовность БД;
- panic recovery логирует request ID и возвращает нейтральный `500`;
- распределённый tracing для монолита MVP необязателен.

## 12. Тестирование

### Backend

- unit: нормализация/валидация логина, функция интервалов, статусы прогресса,
  правила дерева;
- repository integration на реальной PostgreSQL: tenant isolation, recursive
  CTE, ограничения, сортировка кандидатов;
- HTTP integration: auth-cookie, коды ошибок, идемпотентный ответ, продолжение
  сессии;
- race/concurrency test: два одновременных ответа одной позиции создают ровно
  одно событие и одно изменение счётчиков.

### Frontend

- component: форма карточки, переворот, блокировка оценки до reveal, доступность
  кнопок и клавиатуры;
- integration с mock API: пустые/ошибочные состояния и retry;
- Playwright: регистрация → карточка → папка → сессия → итог; продолжение после
  reload; мобильный viewport 360 px.

Тесты алгоритма используют внедряемые clock и random source. Production-код не
должен зависеть от локального времени машины или недетерминированного генератора
в unit-тестах.

## 13. Предлагаемая структура репозитория

```text
cmd/server/main.go
internal/
  auth/
  cards/
  folders/
  study/
  platform/{config,database,httpserver}/
migrations/
web/
  src/{app,features,pages,shared}/
  package.json
docs/
  PRODUCT.md
  ARCHITECTURE.md
go.mod
Makefile
README.md
```

Не создавать абстракции «на будущее» без второго применения. Интерфейсы нужны
на границах модулей или для тестируемых зависимостей (clock/random/repository),
а не для каждой структуры.

## 14. Последовательность реализации

1. Каркас, конфигурация, миграции, health checks, CI.
2. Регистрация/вход/выход и автоматический `Inbox`.
3. CRUD дерева папок и карточек с tenant isolation.
4. Чистый планировщик, preview и создание сессии.
5. Reveal/answer, идемпотентность, продолжение и результат.
6. Адаптивный frontend и доступность основных сценариев.
7. Интеграционные/E2E тесты, security review, production deployment.

Каждый этап должен оставлять приложение запускаемым и сопровождаться миграциями
и минимальными тестами новых инвариантов на самом дешёвом подходящем уровне.
Полный integration/E2E hardening выполняется на этапе 7, а не дублируется в
каждом предыдущем срезе.

## 15. Отложенные решения

Пересматривать после появления реальных данных:

- переход с лестницы интервалов на FSRS;
- оптимизация случайного выбора для очень больших коллекций;
- строгий распределённый rate limit при нескольких репликах;
- отдельная раздача frontend/CDN;
- партиционирование или архивирование `review_events`.

Redis не является автоматическим решением ни для одного из этих пунктов.
