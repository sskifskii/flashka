# Инструкции для агентов

## Источник требований

Перед проектированием или изменением кода полностью прочитайте:

1. `docs/PRODUCT.md` — продуктовые границы, сценарии и критерии приёмки;
2. `docs/ARCHITECTURE.md` — целевая архитектура, данные, API и безопасность;
3. `README.md` — краткий контекст проекта.

Если документы расходятся, продуктовые правила из `PRODUCT.md` определяют
поведение, а `ARCHITECTURE.md` — способ реализации. Не устраняйте существенное
противоречие молча: зафиксируйте решение в обоих документах.

## Границы MVP

- Backend: Go + PostgreSQL. Frontend: React + TypeScript.
- Не добавляйте Redis, внешний кэш, микросервисы или очереди.
- Аутентификация — только логин/пароль и серверная сессия в PostgreSQL.
- Нет email и восстановления пароля. Не проектируйте фиктивный recovery flow.
- Карточка содержит только две текстовые стороны; не приписывайте им языковую
  семантику.
- Сначала реализуйте специфицированное поведение. Любая новая возможность требует
  явного продуктового решения и обновления документации.

## Правила реализации

- Сохраняйте модульный монолит и направление зависимостей, описанные в
  архитектуре.
- Изолируйте все пользовательские запросы по `user_id`; чужой ресурс отвечает
  как несуществующий.
- Учебное расписание вычисляет только backend. Событие ответа, позиция сессии и
  агрегаты карточки обновляются в одной транзакции.
- Используйте серверное UTC-время, внедряемые clock/random в тестируемой логике и
  параметризованные SQL-запросы.
- Не храните и не логируйте пароли, сырые session tokens и тексты карточек.
- Любое изменение схемы оформляйте новой миграцией; не переписывайте уже
  применённую миграцию без отдельного согласования.
- Не вводите абстракцию без текущей потребности. Предпочитайте простой явный код.
- Не меняйте продуктовый алгоритм интервалов или API-контракт без синхронного
  обновления `PRODUCT.md` и `ARCHITECTURE.md`.

## Качество и проверка

- Форматируйте Go через `gofmt`, TypeScript — настроенным formatter/linter.
- Новое доменное правило сопровождайте unit-тестом; SQL-инвариант —
  интеграционным тестом с PostgreSQL; критический пользовательский путь — E2E.
- Особое внимание тестам tenant isolation, циклам папок, одновременным ответам,
  идемпотентности и продолжению сессии после перезагрузки.
- Перед завершением запускайте доступные formatter, lint, test и build команды и
  сообщайте, что именно не удалось проверить.
- Не ослабляйте тест или ограничение ради прохождения сборки без объяснения
  причины.

## Работа с репозиторием

- Сохраняйте чужие незавершённые изменения и не выполняйте разрушительные git-
  операции без явного запроса.
- Делайте изменения небольшими и тематически связанными.
- Обновляйте README только для информации, нужной новому разработчику; детали
  поведения держите в `PRODUCT.md`, технические решения — в `ARCHITECTURE.md`.
- Пока команды проекта не созданы, не выдумывайте их. После появления `Makefile`
  или package scripts поддерживайте здесь краткий список проверенных команд.
