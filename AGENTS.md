# Инструкции для агентов

## Источник требований

Перед работой всегда проверьте `git status`, `docs/ROADMAP.md` и активный feature-spec, если он есть. Затем через оглавление и поиск откройте только относящиеся к задаче разделы `docs/PRODUCT.md`, `docs/ARCHITECTURE.md` и связанные ADR. `DEVELOPMENT.md` перечитывайте при изменении процесса или сомнении в выборе проверок, а `README.md` — только для первого знакомства с проектом.

Полностью перечитывайте документ, только если меняете заданные им правила, обнаружили противоречие или после просмотра оглавления и поиска не можете уверенно определить релевантные границы. Не загружайте весь корпус документации для локального и однозначного изменения.

Если документы расходятся, продуктовые правила из `PRODUCT.md` определяют поведение, а `ARCHITECTURE.md` — способ реализации. Не устраняйте существенное противоречие молча: зафиксируйте решение в обоих документах.

ADR хранит историческое обоснование решения и не заменяет описание актуального состояния в `ARCHITECTURE.md`. Feature-spec уточняет конкретный вертикальный срез и не должен противоречить `PRODUCT.md`.

## Границы MVP

- Backend: Go + PostgreSQL. Frontend: React + TypeScript.
- Не добавляйте Redis, внешний кэш, микросервисы или очереди.
- Аутентификация — только логин/пароль и серверная сессия в PostgreSQL.
- Нет email и восстановления пароля. Не проектируйте фиктивный recovery flow.
- Карточка содержит только две текстовые стороны; не приписывайте им языковую семантику.
- Сначала реализуйте специфицированное поведение. Любая новая возможность требует явного продуктового решения и обновления документации.

## Правила реализации

- Сохраняйте модульный монолит и направление зависимостей, описанные в архитектуре.
- Изолируйте все пользовательские запросы по `user_id`; чужой ресурс отвечает как несуществующий.
- Учебное расписание вычисляет только backend. Событие ответа, позиция сессии и агрегаты карточки обновляются в одной транзакции.
- Используйте серверное UTC-время, внедряемые clock/random в тестируемой логике и параметризованные SQL-запросы.
- Не храните и не логируйте пароли, сырые session tokens и тексты карточек.
- Любое изменение схемы оформляйте новой миграцией; не переписывайте уже применённую миграцию без отдельного согласования.
- Не вводите абстракцию без текущей потребности. Предпочитайте простой явный код.
- Не меняйте продуктовый алгоритм интервалов или API-контракт без синхронного обновления `PRODUCT.md` и `ARCHITECTURE.md`.

## Рабочий процесс

- Реализуйте работу небольшими вертикальными срезами по процессу из `docs/DEVELOPMENT.md`.
- Один главный агент сам выполняет анализ, короткий spec, реализацию и self-review. Субагент или независимый reviewer используется только по прямому запросу пользователя, в том числе для высокорисковых изменений.
- Если всё же используются несколько агентов, они не должны одновременно редактировать одни файлы. Главный агент отвечает за интеграцию и проверку фактического состояния репозитория.
- Сложная функция получает короткий, обычно не длиннее 60 строк, файл `docs/specs/NNNN-short-name.md`. Spec содержит только границы, новые правила и 3–7 критериев; он не дублирует OpenAPI, архитектуру и план тестов. После его самостоятельной проверки сразу начинайте реализацию без отдельной spec-фазы.
- Труднообратимое архитектурное решение оформляется как `docs/adr/NNNN-short-name.md`. Принятый ADR не переписывается задним числом: новое решение помечает его `Superseded` и ссылается на замену.
- Не создавайте spec или ADR для тривиального изменения только ради процесса.
- План конкретной задачи живёт в задаче/PR или сообщении агента; не добавляйте в репозиторий одноразовые plan-файлы.
- OpenAPI становится контрактом API с первого реализованного HTTP-среза и обновляется в том же изменении, что и endpoint.
- В начале новой рабочей сессии сверяйтесь с `docs/ROADMAP.md` и состоянием репозитория. Не полагайтесь на историю предыдущего чата.
- Перед завершением незаконченной работы обновите в roadmap раздел «Точка продолжения»: что готово, что проверено и какое конкретное действие следующее.
- Не начинайте следующий spec, пока текущий срез не отмечен в roadmap как `Done` или `Blocked` с причиной.
- Обращайтесь к пользователю внутри фазы только при настоящем блокере: требуемый выбор существенно меняет продукт, расширяет MVP, создаёт новое труднообратимое решение или требует внешнего разрешения. Обычные технические решения принимайте самостоятельно по существующим документам.
- После `Done` обновите только фактически изменившиеся контракты, ссылку на новый spec и одну строку roadmap. Новый срез можно продолжить в той же сессии, если он входит в запрос пользователя; отдельная сессия или Human Checkpoint не нужны.

## Качество и проверка

- Форматируйте Go через `gofmt`, TypeScript — настроенным formatter/linter.
- Проверяйте новое правило один раз на самом дешёвом подходящем уровне: чистую логику unit-тестом, SQL/tenant/транзакцию точечным integration-тестом, React-поведение component-тестом. Не дублируйте правило на всех уровнях без конкретного риска.
- E2E поддерживает один общий критический smoke-путь. Не добавляйте E2E для каждого edge case, браузера или viewport в отдельном срезе.
- Локально запускайте formatter, компиляцию/typecheck и целевые тесты только затронутой области; при изменении API — OpenAPI validation, при изменении SQL/tenant/транзакции — применение миграции вперёд и один релевантный integration-тест.
- Полный набор команд, race detector, migration `down/up`, production build и полный E2E обязательны только перед пилотом/релизом, при неисправном CI или по явному запросу пользователя. Не повторяйте локально полный CI после каждого среза.
- Сначала реализуйте happy path и обязательные инварианты. Не добавляйте без критерия исчерпывающие UI-состояния, необязательные edge cases, polish, рефакторинг или дополнительное покрытие; перечислите их в итоговом отчёте.
- Не повторяйте уже успешную проверку, если после неё не менялись влияющие на неё файлы. В итоговом отчёте кратко перечислите выполненные и пропущенные проверки.
- Не ослабляйте тест или ограничение ради прохождения сборки без объяснения причины.

## Работа с репозиторием

- Сохраняйте чужие незавершённые изменения и не выполняйте разрушительные git- операции без явного запроса.
- Делайте изменения небольшими и тематически связанными.
- Обновляйте README только для информации, нужной новому разработчику; детали поведения держите в `PRODUCT.md`, технические решения — в `ARCHITECTURE.md`.
- Пока команды проекта не созданы, не выдумывайте их. После появления `Makefile` или package scripts поддерживайте здесь краткий список проверенных команд.

## Проверенные команды проекта

- `make dev` — однокомандный локальный запуск PostgreSQL, миграций, frontend и backend;
- `make fmt-check` — проверка форматирования Go и frontend;
- `make lint` — `go vet`, ESLint и TypeScript typecheck;
- `make test` — Go race/unit и frontend component tests;
- `make test-integration` — тесты с реальной PostgreSQL;
- `make migrate-check` — полный цикл миграций `up/down/up`;
- `make openapi-check` и `make secret-check` — контракт и секреты;
- `make build` — production-сборка frontend и Go binary;
- `make test-e2e` — Playwright E2E при запущенных PostgreSQL и backend.

Это полный набор для пилота/релиза. Для обычного среза выбирайте только затронутые команды и конкретные test files/packages.
