# Инструкции для агентов

## Источник требований

Перед проектированием или изменением кода полностью прочитайте:

1. `docs/PRODUCT.md` — продуктовые границы, сценарии и критерии приёмки;
2. `docs/ARCHITECTURE.md` — целевая архитектура, данные, API и безопасность;
3. `docs/ROADMAP.md` — текущий этап, зависимости и следующий шаг;
4. `docs/DEVELOPMENT.md` — обязательный рабочий процесс и Definition of Done;
5. подходящий документ из `docs/specs/`, если функция уже специфицирована;
6. связанные решения из `docs/adr/`;
7. `README.md` — краткий контекст проекта.

Если документы расходятся, продуктовые правила из `PRODUCT.md` определяют
поведение, а `ARCHITECTURE.md` — способ реализации. Не устраняйте существенное
противоречие молча: зафиксируйте решение в обоих документах.

ADR хранит историческое обоснование решения и не заменяет описание актуального
состояния в `ARCHITECTURE.md`. Feature-spec уточняет конкретный вертикальный
срез и не должен противоречить `PRODUCT.md`.

## Границы MVP

- Backend: Go + PostgreSQL. Frontend: React + TypeScript.
- Не добавляйте Redis, внешний кэш, микросервисы или очереди.
- Аутентификация — только логин/пароль и серверная сессия в PostgreSQL.
- Нет email и восстановления пароля. Не проектируйте фиктивный recovery flow.
- Карточка содержит только две текстовые стороны; не приписывайте им языковую
  семантику.
- Сначала реализуйте специфицированное поведение. Любая новая возможность требует
  явного продуктового решения и обновления документации.

## Правила реализации

- Сохраняйте модульный монолит и направление зависимостей, описанные в
  архитектуре.
- Изолируйте все пользовательские запросы по `user_id`; чужой ресурс отвечает
  как несуществующий.
- Учебное расписание вычисляет только backend. Событие ответа, позиция сессии и
  агрегаты карточки обновляются в одной транзакции.
- Используйте серверное UTC-время, внедряемые clock/random в тестируемой логике и
  параметризованные SQL-запросы.
- Не храните и не логируйте пароли, сырые session tokens и тексты карточек.
- Любое изменение схемы оформляйте новой миграцией; не переписывайте уже
  применённую миграцию без отдельного согласования.
- Не вводите абстракцию без текущей потребности. Предпочитайте простой явный код.
- Не меняйте продуктовый алгоритм интервалов или API-контракт без синхронного
  обновления `PRODUCT.md` и `ARCHITECTURE.md`.

## Рабочий процесс

- Реализуйте работу небольшими вертикальными срезами по процессу из
  `docs/DEVELOPMENT.md`.
- Один вертикальный срез является автономной фазой. Главный агент доводит её от
  `Draft` до `Implemented` без промежуточного Human Checkpoint.
- Если доступны субагенты, главный агент обязан последовательно использовать
  независимые роли автора spec, рецензента spec, implementer и code/QA reviewer.
  Главный агент остаётся ответственным за решения, интеграцию и проверку
  фактического состояния репозитория.
- Рецензенты по умолчанию работают read-only. Одновременно редактировать одни и
  те же файлы нескольким агентам запрещено. Параллельная реализация допустима
  только после фиксации контрактов и для непересекающихся областей файлов.
- Сложная функция до начала реализации получает следующий свободный номер и
  файл `docs/specs/NNNN-short-name.md`. Не резервируйте номера пустыми файлами.
- Труднообратимое архитектурное решение оформляется как
  `docs/adr/NNNN-short-name.md`. Принятый ADR не переписывается задним числом:
  новое решение помечает его `Superseded` и ссылается на замену.
- Не создавайте spec или ADR для тривиального изменения только ради процесса.
- План конкретной задачи живёт в задаче/PR или сообщении агента; не добавляйте в
  репозиторий одноразовые plan-файлы.
- OpenAPI становится контрактом API с первого реализованного HTTP-среза и
  обновляется в том же изменении, что и endpoint.
- В начале новой рабочей сессии сверяйтесь с `docs/ROADMAP.md` и состоянием
  репозитория. Не полагайтесь на историю предыдущего чата.
- Перед завершением незаконченной работы обновите в roadmap раздел «Точка
  продолжения»: что готово, что проверено и какое конкретное действие следующее.
- Не начинайте следующий spec, пока текущий не доведён до `Implemented` или явно
  не помечен `Blocked` с причиной.
- Обращайтесь к пользователю внутри фазы только при настоящем блокере: требуемый
  выбор существенно меняет продукт, расширяет MVP, создаёт новое
  труднообратимое решение или требует внешнего разрешения. Обычные технические
  решения принимайте самостоятельно по существующим документам.
- Human Checkpoint наступает после `Implemented`: обновите spec, его реестр и
  roadmap, сообщите результаты и остановитесь перед следующим срезом.

## Качество и проверка

- Форматируйте Go через `gofmt`, TypeScript — настроенным formatter/linter.
- Новое доменное правило сопровождайте unit-тестом; SQL-инвариант —
  интеграционным тестом с PostgreSQL; критический пользовательский путь — E2E.
- Особое внимание тестам tenant isolation, циклам папок, одновременным ответам,
  идемпотентности и продолжению сессии после перезагрузки.
- Перед завершением запускайте доступные formatter, lint, test и build команды и
  сообщайте, что именно не удалось проверить.
- Не ослабляйте тест или ограничение ради прохождения сборки без объяснения
  причины.

## Работа с репозиторием

- Сохраняйте чужие незавершённые изменения и не выполняйте разрушительные git-
  операции без явного запроса.
- Делайте изменения небольшими и тематически связанными.
- Обновляйте README только для информации, нужной новому разработчику; детали
  поведения держите в `PRODUCT.md`, технические решения — в `ARCHITECTURE.md`.
- Пока команды проекта не созданы, не выдумывайте их. После появления `Makefile`
  или package scripts поддерживайте здесь краткий список проверенных команд.

## Проверенные команды проекта

- `make fmt-check` — проверка форматирования Go и frontend;
- `make lint` — `go vet`, ESLint и TypeScript typecheck;
- `make test` — Go race/unit и frontend component tests;
- `make test-integration` — тесты с реальной PostgreSQL;
- `make migrate-check` — полный цикл миграций `up/down/up`;
- `make openapi-check` и `make secret-check` — контракт и секреты;
- `make build` — production-сборка frontend и Go binary;
- `make test-e2e` — Playwright E2E при запущенных PostgreSQL и backend.
