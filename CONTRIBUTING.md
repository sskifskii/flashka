# Участие в Flashka

Спасибо за интерес к проекту! Принимаются исправления, улучшения документации
и предложения через [Issues](https://github.com/Skifskii/flashka/issues).
Issues и pull requests можно писать на русском или английском.
Общайтесь уважительно; обсуждайте идеи и код без личных нападок.

## До начала работы

1. Прочитайте [README](README.md) и [roadmap](docs/ROADMAP.md), проверьте
   существующие Issues и PR, чтобы не дублировать работу.
2. Для новой возможности или изменения алгоритма сначала откройте Issue и
   согласуйте границы с сопровождающим: MVP намеренно ограничен.
3. Для исправления ошибки или опечатки можно сразу прислать небольшой PR.

Текущее поведение определяет [PRODUCT.md](docs/PRODUCT.md), устройство системы —
[ARCHITECTURE.md](docs/ARCHITECTURE.md). Публикация исходников не расширяет
продуктовые границы MVP. При использовании кодовых агентов учитывайте
[AGENTS.md](AGENTS.md).

## Подготовка pull request

- Создайте fork и отдельную ветку от актуальной default branch репозитория.
- Следуйте [локальному запуску](README.md#быстрый-старт).
- Делайте один тематически связанный набор изменений. Опишите проблему,
  результат и способ проверки; для UI приложите снимок экрана без личных данных.
- Меняйте документацию и OpenAPI вместе с соответствующим поведением или API.
  Изменения БД оформляйте новой миграцией.
- Добавляйте целевой тест для нового правила на подходящем уровне; для простой
  правки документации достаточно проверки ссылок и `git diff --check`.
- Запускайте проверки затронутой области по
  [процессу разработки](docs/DEVELOPMENT.md#8-проверки). Укажите выполненные и
  пропущенные проверки в PR. Полный набор выполняет CI.
- Не включайте `.env`, дампы, ключи, токены, реальные карточки и персональные
  данные пользователей, в том числе в логи и скриншоты.

Для миграционных и integration-проверок используйте отдельную тестовую БД.
`make migrate-check` удаляет схему при выполнении down; не запускайте его на
данных, которые нужно сохранить.

Следуйте [SECURITY.md](SECURITY.md).
